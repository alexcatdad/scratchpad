# Remaining product verification ledger

This ledger tracks the owner's request to build the rest of Scratchpad. Its authority is the current [PRD](prd.md), [architecture](architecture.md), [API contract](api.md), and accepted clarifications. The completed SQLite MVP is the starting point, not the completion definition for this work.

## Status and evidence rules

The baseline below was inspected on 1 October 2026 before remaining-product implementation. **Pending** means completion is unproven; it does not mean that implementation is prohibited or that a future code change has been audited. Existing MVP tests provide regression evidence only within their actual coverage. Update this ledger with exact committed revisions, commands, runtime results, and release identifiers as acceptance proceeds.

Synthetic fixtures are valid acceptance inputs. USB Boop and other real projects are illustrative datasets, not a source of product requirements or historical truth (PRD §43). Label synthetic content explicitly. Never send private project data to an AI provider during verification without the owner's authorization.

## Scope boundaries

PRD §7 continues to exclude teams/RBAC, enterprise identity, billing, project management, destructive AI cleanup and mandatory cloud/vector infrastructure. Adding PostgreSQL does not require pgvector: it is explicitly a later option. Generating private downloadable documents does not require public hosting or collaborative access.

GitHub profile enrichment is explicitly optional in PRD §28 and architecture §6.3. Owner-profile presentation is still included in dashboard configuration. API examples and architecture screen paths are conceptual where labeled as such; implement their behaviors without treating illustrative spelling as mandatory. OpenAPI publication is expected eventually by API §58; generated clients are optional and not a reason to change the Go/HTTP boundary.

PRD §41 permits tuning prompts, thresholds, schedules, scoring, schema details and information architecture through use. It does not permit omitting the named capabilities. Keep those settings adaptable without rewriting immutable sources.

## Completion audit

For each row, record the exact evidence that proves behavior, its scope and limits. A passing stub-provider test alone does not prove selected LM Studio interoperability; a successful provider request alone does not prove application generation/search. One database passing tests does not establish the other engine. A local build does not establish canonical CI, release publication or an updated local deployment. Keep incomplete or indirect evidence marked pending.
