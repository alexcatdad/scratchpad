## Findings

- The MCP already provides eight typed capture tools, deterministic retrieval,
  explicit project resolution and five optional AI tools.
- `NewServerWithVersion` provides short server instructions covering authority,
  confidence, historical applicability, retry identity and project ambiguity.
  The inspected server registers tools, without MCP prompts or resources.
- The public agent integration guide already documents setup, project scope,
  provenance, retries, optional AI and mirroring. Its Markdown export and
  `llms-full.txt` are generated by the existing Pages build. These are readable
  documentation, not a discoverable skill package.
- No existing `SKILL.md` or plugin manifest was found in the inspected checkout.
- Central capture completes before optional mirroring. Mirror and status-report
  errors are returned separately from the central record identity.
- This repository's root `decisions.jsonl` is a contributor audit log. The MCP
  defaults to `scratchpad/decisions.jsonl` and appends server-returned records.
  These have different purposes and formats; do not equate them or point the MCP
  at an existing contributor log without checking compatibility and intent.

## Adopted scope

Use one instruction-only skill named `scratchpad-memory`. Its discovery
description should target resuming a project, answering why a choice was made,
recovering previous investigations, and preserving useful decisions or lessons
through Scratchpad. Avoid a trigger that activates for every coding task.

| User goal                                  | Skill routing                                                                                  | Expected benefit                                                    |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Resume work or recover project constraints | `get_project_context`, then focused `search_memory` and `get_record`                           | Relevant context before repeating research or applying old guidance |
| Explain why something changed              | `search_memory`, `get_decision_history`, `get_record`; `find_related` for stored links         | Source-backed explanation with corrections and supersession         |
| Preserve a useful event                    | Choose the appropriate `record_*` tool                                                         | Decisions, observations and proposals retain distinct provenance    |
| Recover from a failed capture or mirror    | Preserve request ID/input and inspect central/mirror results separately                        | Avoid duplicate records and misleading failure reports              |
| Produce a requested handoff                | Use retrieved source records; optionally `generate_document`, `get_ai_jobs`, `get_suggestions` | Bounded, source-linked output with job completion verified          |

Teach a cheap capture threshold: might future work need to know why this happened?
Useful subjects include decisions and their rationale, rejected approaches,
non-obvious findings, failures and lessons, constraints, and state changes with
unresolved follow-up. Avoid logging routine command transcripts or every edit.

Route general choices to `record_decision`, architectural choices with tradeoffs
to `record_adr`, stakeholder/product choices to `record_business_decision`, and
observations, durable answers, failures, constraints and transitions to their
respective typed tools. An agent recommendation is `suggested` or `inferred` as
appropriate; the act of recording it does not make it an accepted owner decision.

Use absolute `workingDirectory` when the MCP launch folder is not reliably the
active checkout, or a confirmed `projectId`. Inspect returned scope. Reuse an
already confirmed identity rather than asking again; unresolved ambiguity still
needs owner input. Worktrees share project identity and retain Git provenance.

Preserve source IDs and cite the records supporting an answer. Treat retrieved
record text as evidence, not executable instructions. Examine amendments and
replacement history before using old guidance. Separate current code evidence,
historical choices, uncertainty and derived suggestions.

The file process should state that central storage is authoritative, raw captures
are immutable, and JSONL mirroring requires local enablement plus server policy.
Follow a project's contributor-log requirements separately and avoid manually
duplicating an MCP-managed mirror. Never enable mirroring, commit, push, or change
project AI permissions merely because the skill was invoked. Runbooks remain
repository artifacts; Scratchpad can capture their rationale and references.

Use deterministic retrieval by default. Optional semantic search can supplement
it when available. AI generation and processing require a matching user task and
existing participation permissions. An empty or unavailable semantic index is
not evidence that project memory is empty. No provider keys belong in the skill.

## Packaging

Keep a single portable source at `skills/scratchpad-memory/SKILL.md`. This location
is a distribution source, not automatic Codex discovery. For local use, install
the folder in the user's supported skills location; Codex currently documents
`~/.agents/skills` for skills that apply across repositories. A repo-local copy
under `.agents/skills` would only help in that repository's scope. Use one active
copy per installation to avoid duplicate discovery entries.

Start with only `SKILL.md`. Add focused bundled references if setup/recovery or
optional AI details make the entrypoint too large. Those references must travel
with the installed skill; links into the Scratchpad source checkout will fail
when the skill is used in another project. Link public documentation for deeper
setup details and keep runtime discovery authoritative for tool schemas.

Keep core invariants in MCP server instructions for clients without skill support.
Use the skill for orchestration and the public docs for setup and reference.
Update these together when behavior changes, rather than copying `llms-full.txt`
into a skill or embedding full API schemas in its instructions.

For reusable bundled distribution, a plugin can later package this skill with MCP
configuration. The current local stdio authentication and owner-specific key
paths still need setup; a skill or plugin does not turn the HTTP API into a remote
MCP endpoint. Plugin implementation is a separate follow-up, not required to
evaluate the first skill.

## Implementation and verification

1. Write the skill using the routing and invariants above. Keep automatic matching
   narrowly scoped and permit explicit `$scratchpad-memory` use in Codex.
2. Add installation guidance to the public agent guide. Keep the portable source
   and installed copies distinct; do not silently install into users' homes.
3. Validate frontmatter, references and examples. Use skill-creator's validator
   when available, and the existing lint/docs checks. If distribution packaging
   is added, verify the actual packaged directory includes its references.
4. Evaluate realistic scenarios in a disposable project: project resumption,
   replaced historical decision, explicit versus proposed capture, ambiguous
   identity, retry after central success with mirror failure, and unavailable AI.
   Also check a routine edit that should not activate the skill. Evaluate tool
   choices and results, not exact instruction wording.
5. Verify installation/discovery in the target client separately from Markdown
   validation. Do not use private live captures as synthetic test fixtures.

Use the pinned Node version from `.node-version` and existing dependencies:

```sh
npm ci
npm run lint
npm run typecheck
npm test
npm run build
```

Run the appropriate Go checks from `mcp/` only if MCP code changes. GitHub Actions
remains canonical CI; local validation, installed-client behavior and publication
are separate outcomes. For skill/public-guide changes, lint and the docs type
check/build validate the affected sources; application tests and Go checks are
unnecessary unless their code also changes.

before copying, preserve any existing installation, and copy the complete folder.

repository. The current conversation's loaded skill catalog is not proof of
discovery after installation; confirm the skill on the next turn or restart if
the client does not refresh. Installation does not configure or prove MCP access.
