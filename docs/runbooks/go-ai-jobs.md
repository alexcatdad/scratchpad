# Go durable AI job controls

The development Go backend implements `GET /api/v1/ai/jobs`, `POST /ai/jobs` and `POST /ai/jobs/{id}/retry`, plus embedding/analysis/export execution, automatic scheduling, `POST /search/semantic`, suggestion listing/review and `POST /summaries/export`. The TypeScript application remains the supported runtime until issue 36 passes full parity and delivery acceptance. Both manual and scheduled work execute under persisted leases.

Enqueue accepts `type: analyze | embed | export`, one `projectId` or explicit `projectIds`, optional `crossProject` and the existing export formats. It returns HTTP 202 with the persisted job. Jobs start queued with attempts zero, version one, a current run-after time and canonical selected project IDs. Default export format is `handoff`. Provider configuration must be enabled, and a configured token must be usable through the retained key; enqueue does not contact the provider or wait for model availability.

Single-project operations require one selected project and AI consent. Explicit cross-project selections require every selected project to permit AI and cross-project participation; denied or missing projects fail instead of being silently dropped. Implicit cross-project requests select only participating projects. Explicit lookup uses selected identities rather than scanning unrelated records. Jobs remain operational state and are excluded from portable knowledge export.

Retry requires a failed job, its current expected version/`If-Match`, usable configuration and renewed current scope consent. It retains identity, original scope/type/format and creation provenance, increments the version and resets queued state, attempts, error/completion and lease fields. Queued/running/completed jobs cannot be retried through this interface. Enqueue/retry and their acting-owner audits share one serialized write transaction.

Each server checks for work every second and executes one job at a time. Serialized claims persist a distinct lease token, increment attempts and recover expired running leases. Leases last the configured provider timeout plus thirty seconds and renew before each provider request. At most three attempts run automatically, with exponential retry delays. Shutdown cancels provider work and leaves interrupted leases recoverable. Worker failures do not affect core readiness.

With a nonzero `scheduleMinutes`, the worker persists an `ai_schedule` next-run deadline and queues eligible work when it is due. Each consenting project receives embedding and, when analysis modes are selected, analysis work. Two or more cross-project participants also receive one cross-project analysis job. Existing queued/running work suppresses overlapping jobs; active cross-project analysis covers its participating projects as well as preventing a duplicate cross-project cycle. Analysis modes can be empty for embedding-only schedules. A schedule of zero keeps automatic processing off while manual jobs remain available.

The entire due cycle shares the existing serialized transaction: current configuration/secret/consent checks, queue entries and audits, and the next deadline commit together. Late failures leave no partial cycle and do not postpone its deadline. Concurrent servers and restarts respect the persisted deadline. Enqueueing does not call the provider. Schedule state stays in full operational snapshots and is excluded from portable knowledge archives.

Consent, usable secret state, configuration generation and lease ownership are checked before each provider dispatch and before result activation. Provider waits occur outside database writes. Embedding upserts, completion state and the completion audit commit together. Configuration changes or consent revocation discard in-flight results; no later request is admitted under stale settings. Provider failures retain safe fixed errors, without response bodies or tokens.

This slice preserves the existing whole-record semantic projection on SQLite and PostgreSQL. It processes all content in bounded chunks, preserving Unicode characters at boundaries, and combines chunk vectors only for this legacy projection. Compatible fingerprints and canonical source hashes determine semantic eligibility. Query embeddings require current consent; results are revalidated after ranking. An absent compatible index returns `indexRequired: true`. The new PostgreSQL RAG projection still requires separate passages and embedding compatibility independent of completion-model selection; these legacy vectors do not fulfill that requirement.

## Analysis and private documents

Analysis sends bounded record fragments and permitted project names to the configured completion provider, interleaving projects so earlier history does not crowd out another project's inputs. Long records remain complete and Unicode characters remain intact at fragment boundaries. Requests use strict structured-output schemas, configured output limits and reasoning effort. Optional null placeholders are removed only from known optional fields; required fields are validated before analysis-mode filtering. Per-kind content and source validation reject unsupported relationship replacement, invalid endpoints, missing Markdown or citations outside the supplied batch.

The server assigns derived/pending/private status, generator and job provenance, cited projects and complete `privacyDependencies` for every supplied record and project metadata input. Model-provided authority or privacy fields cannot narrow those dependencies. Insufficient-evidence candidates are omitted with safe warnings; a response containing only unsupported evidence fails rather than reporting completed suggestions. Valid artifacts, warnings, completion state and audits activate together under renewed consent, source, configuration and lease checks.

`POST /api/v1/summaries/export` shares durable enqueueing and forces the export job type. It supports the existing formats and consent rules. Export generation works independently of the selected analysis modes and requests one compact Markdown artifact per batch. Multiple sections consolidate into one private draft retaining every processed source and input dependency. The server adds source links and the AI-draft notice. Generation does not publish a document or accept it as an owner decision; sharing remains a separate action.

## Suggestions and review

`GET /api/v1/suggestions` reads valid stored artifacts under current AI enablement and project consent. Optional `projectId`, repeated `projectIds` and `crossProject` constrain the view. Source citations and complete privacy dependencies are distinct: every input project must remain permitted and fit the requested scope, even when it was not cited in the displayed output. Invalid historical content, missing sources and unknown legacy privacy provenance remain preserved in knowledge archives but are hidden from suggestions. Selected project views filter candidates in SQL; source and project validation loads only referenced identities in batches.

`POST /suggestions/{id}/accept` and `/reject` require the current version or `If-Match`. Review independently validates stored content, references and consent inside the serialized transaction. Acceptance records a separate private curated artifact retaining derived authority, generator, citations and complete dependencies. Original captures remain unchanged. When exactly one actual dependency project participates, classification can update audited metadata and eligible relationship candidates/contradictions create accepted edges with suggested authority and explicit AI derivation. Cross-project interpretations stay in curated artifacts without being copied into local metadata or relationships. A cross-project request involving one actual project still retains eligible local effects, subject to cross-project consent.

Rejection records review status and actor without creating curated evidence. Both actions are single-use optimistic transitions, with all effects and audits committed atomically. Listing and review do not contact a provider or require decryption of its token; AI enablement and current consent still gate access. Historical missing citations return `AI_ARTIFACT_INVALID` during review, and unknown privacy provenance fails closed. Provider availability does not prevent reviewing valid historical suggestions.

## Verification

```sh
npm run test:backend
```

Supply disposable `TEST_POSTGRES_URL` for PostgreSQL. Real-process HTTP tests cover durable enqueue/list/restart, failed-job optimistic retry, scope consent, provider-outage-independent enqueue and late audit rollback. Embedding workflows verify semantic retrieval across restart, abandoned-lease recovery with competing servers and consent revocation during provider waits on both engines. A long-record fixture verifies Unicode preservation. Operational SQLite backup/restore verifies durable execution state independently of the live source. Synthetic provider responses replace only the external network boundary. These checks do not establish PostgreSQL operational restore, new passage RAG or deployed acceptance.

Suggestion workflows use the real native import, HTTP listing/review, source detail and knowledge export boundaries. They verify immutable captures, derived provenance, classification and relationship effects, versioned rejection across restart, uncited input-project consent, cross-project isolation, malformed historical content and late audit rollback on both engines. SQL fault/corruption fixtures are inputs; verification reads the public API. No generated completion is claimed by these historical-artifact tests.

Completion workflows verify generated reviewable classification, all existing artifact kinds and insufficient-evidence warnings, complete long-history document consolidation, server-owned privacy despite narrower model citations, malformed-output retry exhaustion, mid-request consent/configuration changes and atomic rollback after a completion audit fault. The existing `mcp/ai-integration` command verifies all five optional tools through actual authenticated stdio processes on SQLite and PostgreSQL, including source detail reads, project consent, semantic retrieval and private handoff generation. The completion provider is synthetic; real model quality and deployment acceptance remain separate.

Scheduler workflows verify concurrent instances/restart, active cross-project deduplication, manual-only mode, real embedding-only processing and complete-cycle rollback on both engines. An operational SQLite restore preserves the deadline and existing job identity without rescheduling. SQL fault and historical-row fixtures are inputs; verification uses public jobs and retrieval.
